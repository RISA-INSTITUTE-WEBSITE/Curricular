## 1. Module purpose

This module develops students’ ability to plan, specify, design, implement, verify and maintain software through an accountable team-based process. Students use engineering practices and documentation to turn stakeholder needs into a tested, maintainable software product.

**Curriculum alignment:** The original handwritten overview characterizes Software Engineering as building large software systems but does not list specific topics. All detailed content below is a **new proposal** for academic review rather than a transcription of source material.

## 2. Proposed module learning outcomes

**Upon successful completion of CS301, students should be able to:**

| Code | Learning outcome |
| --- | --- |
| **LO1** | Explain the goals of software engineering and compare iterative, agile and plan-driven software development approaches for given project constraints. |
| **LO2** | Elicit, analyse and document functional and non-functional requirements, identifying ambiguous, conflicting or unverifiable statements. |
| **LO3** | Develop a coherent software requirements specification with testable acceptance criteria, scope and stakeholder assumptions. |
| **LO4** | Design and communicate a modular system architecture using suitable models or diagrams, interfaces and separation of concerns. |
| **LO5** | Apply introductory design principles such as cohesion, coupling, encapsulation and maintainability when developing software components. |
| **LO6** | Use version control and a collaborative review process to manage changes, issues, traceability and integration of team contributions. |
| **LO7** | Plan and implement unit and integration tests, connect them to requirements, and interpret test results and defect reports. |
| **LO8** | Describe and apply introductory quality-assurance, continuous-integration and configuration-management practices in a controlled project. |
| **LO9** | Identify and address software security, privacy, accessibility and professional-ethics considerations throughout a software lifecycle. |
| **LO10** | Deliver and evaluate a documented small-team software project, including requirements, design decisions, implementation, tests and a reflection on limitations. |

## 3. Learning outcomes by teaching section

### Section A — Lifecycle, Requirements and Design

**Mapped outcomes:** LO1, LO2, LO3, LO4

**Content focus:**
- Software engineering scope, lifecycle models and project constraints
- Stakeholder analysis, elicitation and ambiguity resolution
- Functional/non-functional requirements, SRS and acceptance criteria
- Architecture views, interfaces, components and basic diagrams

### Section B — Implementation Practices, Testing and Responsible Engineering

**Mapped outcomes:** LO5, LO6, LO7, LO8, LO9

**Content focus:**
- Cohesion, coupling, modularity and design trade-offs
- Git branches, issues, code review and traceability
- Unit/integration testing, defect reporting and regression checks
- Introductory CI and configuration management
- Secure development, privacy, accessibility and ethics

### Section C — Team Project and Engineering Evidence

**Mapped outcomes:** LO10; integrates LO1–LO9

**Content focus:**
- Team roles and staged deliverables
- Requirements-to-test traceability
- Reviewable source, working build and documented verification
- Risk register, change decisions and reflective evaluation

## 4. Suggested practical learning and assessment activities

These activities are **proposals**, not a finalized assessment specification.

| Practical activity | Outcomes assessed |
| --- | --- |
| Compare lifecycle approaches for a small application and justify a selection. | LO1 |
| Interview a simulated client and rewrite ambiguous requirements. | LO2, LO3 |
| Produce a short SRS with verifiable acceptance criteria. | LO3 |
| Draft a component diagram and justify key interface decisions. | LO4, LO5 |
| Use feature branches, pull requests and review comments on a team repository. | LO6 |
| Write unit and integration tests that trace to stated requirements. | LO7 |
| Configure a simple CI check to run tests on submitted changes. | LO8 |
| Complete a threat, privacy and accessibility checklist for the project. | LO9 |
| Submit a small-team application with design, tests, change log and project review. | LO1–LO10 |

## 5. Recommended teaching boundaries

- **Prerequisite knowledge:** Build on CS102 programming and, where available, CS201 data structures and CS221 database concepts; do not present these as formally approved prerequisites until reviewed.
- **Team practice:** Require reproducible individual contributions, defined roles and transparent review history, not solely a polished final application.
- **Scope:** Use an achievable small-team project; advanced enterprise architecture, exhaustive formal verification and production-scale DevOps are out of scope.
- **Quality:** Emphasize evidence of requirements analysis, design rationale, testing and responsible software practice.
